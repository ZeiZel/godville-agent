# Контракт реализации автономного агента

## Обязательный результат

Репозиторий должен поставлять Bun 1.4.2/TypeScript-приложение с SQLite, Docker-образом и двумя адаптерами исполнения: `dry-run` по умолчанию и браузерным адаптером, включаемым только явной настройкой. Автоматические тесты используют фикстуры; явно запрошенный владельцем live one-cycle выполняется только через проверенный adapter и journal gate. Конфигурация примера задаёт `reserve_charges=100`; баланс зарядов остаётся неизвестным до подтверждённого наблюдения.

Автоматизация конфликтует с опубликованными правилами Godville. Документация обязана сохранять этот факт и не обещать отсутствие санкций. Запрещены функции и формулировки про stealth, обход обнаружения, CAPTCHA или маскировку. Допустимы настраиваемые `reactionDelayMs` и ограниченные `clickOffsetPx`/`clickJigglePx` для вариативности исполнения и устойчивости UI-тестов.

## Данные SQLite

Минимальная схема содержит:

- `observations`: нормализованные снимки UI/API, время, источник, версия схемы и hash;
- `knowledge`: курируемые игровые факты, приоритет источника, URL, дата проверки, версия и статус;
- `operations`: намерение, handler/version, precondition, результат клика, postcondition, timestamps и состояние `PLANNED|SKIPPED|EXECUTED|CONFIRMED|AMBIGUOUS|FAILED`;
- `decisions`: выбранная цель, входные observation/knowledge ids, rule version и объяснение;
- `handler_catalog`: неизменяемые версии точных role/text-селекторов, предусловий и постусловий;
- `user_settings` и `user_priorities`: версионированные пользовательские настройки и порядок целей с временем вступления в силу;
- `cooldowns` и `charge_ledger`: подтверждённые сроки и раздельный учёт зарядов/резервов.

Каждое решение воспроизводится по сохранённым версиям. Знание без URL и даты проверки не управляет кликом. Приоритет: официальный источник, затем курируемая статья Энциклобогии, затем явно помеченная эвристика. Конфликт знаний сохраняется и блокирует зависимое действие; новая запись не перезаписывает историю.

## Граф целей

Планировщик использует DAG:

```text
temple -> ark -> pairs -> personal_boss
temple -> pension -> shop
personal_boss -> book -> souls
shop + souls -> reliquary
souls + feature_conditions -> annexes
ark + late_game_conditions -> leviathans
```

После открытия узла дочерние ветви конкурируют по конфигурируемому приоритету и текущему узкому месту. При равных условиях порядок: безопасность и резерв, ближайшая постоянная разблокировка, пенсия/магазин, ковчег/пары/личный босс, книга/души, затем доступные поздние возможности — реликварий, приделы и левиафаны. Их дополнительные игровые условия берутся из курируемых знаний. Пользовательские приоритеты версионируются; неизвестная веха вызывает наблюдение, а не предположение.

## Контракт кнопки

Каждый handler имеет неизменяемую версию и задаёт точные `role` и видимый `text`, предусловие, действие и наблюдаемое постусловие. Частичное совпадение текста, индекс элемента и CSS-класс недостаточны. Перед кликом состояние перечитывается; после клика handler ждёт постусловие. Неизвестный UI, несколько совпадений или тайм-аут дают `SKIPPED`/`AMBIGUOUS` без автоматического повтора.

```json
{
  "handler": "arena.zpg.start",
  "version": 1,
  "match": {"role": "button", "text": "<exact curated text>"},
  "preconditions": ["zpg_confirmed", "hour_window_open", "attempt_cooldown_elapsed"],
  "action": {"kind": "click", "reactionDelayMs": [250, 900], "clickOffsetPx": 2, "clickJigglePx": 1},
  "postcondition": {"observation": "mode", "equals": "ZPG_ARENA"},
  "onMismatch": "SKIP",
  "onTimeout": "AMBIGUOUS"
}
```

Диапазоны задержки и сдвига имеют жёсткие верхние границы конфигурации. Они не меняют селектор, предусловия, cooldown или политику повторов. После случайной задержки handler повторно проверяет все предусловия непосредственно перед фактическим кликом. Для временного окна расчётный deadline включает safety margin; если клик нельзя завершить не позднее `HH:02:59` с этим запасом, операция пропускается.

## Алгоритм ZPG-арены

1. Планировщик пытается использовать самый ранний доступный тик в `HH:00:00..HH:02:59`. После позднего запуска или рестарта он может использовать оставшуюся часть окна, если после задержки, повторной проверки и safety margin клик гарантированно укладывается до `HH:02:59`; прошедший `:00` сам по себе не отменяет попытку.
2. Читает авторитетный cooldown из свежего UI. После состоявшегося боя ожидается ориентир четыре часа, после отсутствия соперника — один час; фактический UI-таймер имеет приоритет над этими значениями. Ежечасная проверка определяет право на попытку и не означает обязательный бой.
3. Получает новое UI-наблюдение и требует явного подтверждения ZPG-варианта и точной кнопки handler-а.
4. При отсутствии ZPG отменяет действие. Обычная арена не является fallback.
5. Создаёт один intent, применяет задержку, затем повторно проверяет ZPG, точную кнопку, UI-cooldown и deadline. После клика проверяет постусловие и записывает наблюдаемый результат: состоявшийся бой, отсутствие соперника либо неоднозначность. Cooldown сохраняется из подтверждённого UI, а не выводится только из факта клика.
6. Не использует влияния и гласы во время ZPG и не начисляет ожидаемую награду зарядом.

Механика сверяется с курируемой статьёй [«Арена»](https://wiki.godville.net/Арена); конкретный текст кнопки попадает в каталог handler-ов только после фикстуры UI.

## Приёмка фаз

| Фаза | Результат | Критерий |
|---|---|---|
| A | TypeScript, config, SQLite migrations, Docker | чистый контейнер стартует в `dry-run`; миграции и integrity check проходят |
| B | observation/knowledge/operation stores | replay одного снимка даёт тот же decision и не дублирует operation |
| C | DAG и приоритеты | fixtures покрывают зависимость `personal_boss -> book -> souls`, параллельные ветви и поздние возможности реликвария, приделов и левиафанов |
| D | versioned button handlers | точная роль/текст, pre/postcondition и mismatch/timeout проверены фикстурами |
| E | ZPG scheduler | тесты границ `:00:00`, safety margin перед `:02:59`, `:03:00`, позднего рестарта, UI-cooldown 1/4 ч и отсутствия fallback проходят |
| F | browser adapter | opt-in флаг обязателен; dry-run остаётся default; тесты используют локальные страницы |
| G | эксплуатация | backup/restore, structured logs без секретов и recovery `AMBIGUOUS` проверены |

Готовность не означает разрешение на эксплуатацию и не является обещанием результата игры. Реальный аккаунт не используется в автоматической приёмке.
