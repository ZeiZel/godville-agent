# Архитектура агента Godville

## 1. Статус и границы решения

Документ описывает архитектуру для одного аккаунта Godville. Это спецификация, а не реализация и не инструкция по обходу ограничений игры.

На дату подготовки документа правила Godville запрещают автоматизацию игры, включая автоматический вход и любые прямые или косвенные воздействия на героя без непосредственного участия владельца, а также автоматическое сканирование игровых страниц. Исключение сделано для официального API при наблюдении за собственным героем. Возможные последствия нарушения включают ограничение функций и блокировку аккаунта. Правила могут меняться без уведомления. Источник: [«Правила хорошего тона»](https://godville.net/login/rules).

Архитектура разделена на два контура с общей моделью решений:

1. **Dry-run по умолчанию:** получает данные, рассчитывает решения и записывает намерения без игровых кликов.
2. **Браузерный исполнитель:** opt-in адаптер тех же решений. Его использование конфликтует с действующими правилами; включение не устраняет риск ограничений или блокировки.

Даже подтверждение действия пользователем во внешнем интерфейсе не делает последующий автоматический клик допустимым: безопасная текущая граница — рекомендация, после которой пользователь самостоятельно действует в официальном интерфейсе.

## 2. Проверенные возможности и ограничения данных

Официальный API возвращает JSON для открытого или приватного адреса героя. Приватный токен выдаётся владельцу в профиле и может быть сброшен. Данные обновляются примерно раз в минуту; частые запросы бессмысленны и могут привести к прекращению выдачи. Поля приватного ответа включают, в частности, здоровье, прану, число предметов, активируемые предметы, задание, признак боя и тип режима. Ответ может содержать признак устаревания. Источник: [«API — Энциклобогия»](https://wiki.godville.net/API).

Официальный API является наблюдательным интерфейсом. Документированного API для запуска арены, плавания, подземелья, применения предмета, управления боем с боссом или пенсионных операций не обнаружено.

### Матрица возможностей

| Возможность | Официальный API | Dry-run | Браузерный исполнитель |
|---|---|---|---|
| Идентификация собственного героя | Да | Наблюдение | Предусловие |
| Здоровье, прана, режим боя | Приватные поля | Рекомендации | Перепроверка перед действием |
| Активируемые предметы | Список доступен | Только рекомендация | Только белый список |
| Баланс зарядов | Не подтверждён документацией API | Неизвестен до разрешённого ввода владельца | Требует разрешённого источника |
| Цена пополнения праны зарядом | Не подтверждена как поле API | Версионированное правило, подтверждаемое владельцем | Проверка по разрешённому UI |
| Карта и текущий ход плавания/подземелья | Не подтверждены | Недоступны для автоматической навигации | Требуют разрешённого UI |
| Запуск режима или влияние | Нет | Запрещено | Условно через UI |
| Вход в аккаунт | Нет | Не выполняется | Условно, но сейчас запрещён |

Неизвестные или отсутствующие возможности трактуются как отсутствие данных. Система не должна угадывать баланс, цену, карту, доступность режима или результат действия.

Режим «настроить и забыть» не гарантируется: токен и сессия могут истечь, API — вернуть `expired`, а формат и правила игры — измениться. Тогда советник останавливает зависимые рекомендации и требует реального посещения владельцем; автоматический вход не используется. Баланс зарядов и карта не считаются наблюдаемыми через API без документированного поля. В условном контуре их отображение в аутентифицированном DOM является отдельной, версионированной capability.

## 3. Выбор технологического стека

Для MVP предлагаются Node.js текущей LTS-линии на момент реализации и TypeScript. Конкретную версию фиксируют в lock-файле и образе при начале реализации после проверки официального графика релизов Node.js. Причины выбора: единый типизированный код для получения JSON, правил, уведомлений и будущего адаптера Playwright; простой Docker-образ; развитая поддержка схем JSON.

Для условного исполнителя выбран Playwright с TypeScript. Python не даёт заметного преимущества для этой задачи, а Go потребовал бы отдельного браузерного слоя и усложнил бы поддержку изменчивого интерфейса. Playwright не входит в production-образ MVP.

Решения принимает детерминированный движок правил. Runtime-LLM не используется: он усложнил бы воспроизводимость, аудит расходов и доказательство ограничений.

Для одного аккаунта оптимален один процесс и SQLite в режиме WAL. PostgreSQL на этом масштабе создаёт лишние эксплуатационные расходы. Он остаётся допустимой будущей заменой при нескольких аккаунтах, нескольких узлах или необходимости централизованной высокой доступности.

## 4. Компоненты MVP

Один процесс содержит логически разделённые компоненты:

- **Scheduler** запускает наблюдение с интервалом не чаще обновления API, с jitter и экспоненциальной паузой при ошибках.
- **OfficialApiClient** обращается только к приватному API собственного героя. Схема ответа проверяется, неизвестные поля сохраняются только в диагностическом виде без автоматического использования.
- **ObservationNormalizer** преобразует ответ в версионированную модель наблюдения и явно отмечает отсутствующие, устаревшие и неподтверждённые данные.
- **RuleEngine** применяет чистые версионированные правила к наблюдению и бюджету. Результат — рекомендация или `NoOp` с кодом причины.
- **BudgetLedger** ведёт известный баланс зарядов, обязательства и подтверждённые владельцем расходы. Поскольку API-баланс может быть недоступен, ручное обновление баланса является доверенным вводом с отметкой времени и источника.
- **Notifier** отправляет рекомендацию владельцу по настроенному каналу. Уведомление не выполняет действия в игре.
- **SQLiteStore** хранит наблюдения, решения, журнал бюджета, конфигурацию правил и аудит.

Сетевой allowlist MVP должен разрешать только официальный API собственного героя и явно настроенный канал уведомлений. В образе отсутствуют Chromium, Playwright и код автоматического входа.

## 5. Версионированные контракты

Каждая запись содержит версии контракта и правил, чтобы старое решение можно было воспроизвести:

- `ObservationV1`: герой, время получения, время актуальности, признак `expired`, набор присутствующих возможностей, здоровье, прана, режим, прогресс, инвентарь и список активируемых предметов;
- `CapabilitySetV1`: `api_private`, `charge_balance_known`, `charge_conversion_known`, `map_known` и другие флаги с доказательством источника;
- `RuleSetV1`: пороги здоровья, приоритеты режимов, лимиты рекомендаций и версии стоимостной модели;
- `DecisionV1`: идентификатор наблюдения, версия правил, рекомендация, предпосылки, максимальная стоимость и причины отказа;
- `BudgetEventV1`: ввод баланса, резервирование, подтверждённый расход, отмена, коррекция и внешний расход;
- `NotificationV1`: решение, канал, время и результат доставки.

Изменение смысла поля или правила требует новой версии. Миграция не должна переписывать исторические решения.

## 6. Состояния и правила рекомендаций

Верхний автомат MVP:

`BOOT -> AUTH_CHECK -> OBSERVE -> EVALUATE -> NOTIFY | NO_OP -> WAIT`.

Аварийные состояния: `AUTH_DEGRADED`, `API_EXPIRED`, `SCHEMA_UNKNOWN`, `BUDGET_UNKNOWN`, `BUDGET_LOCK` и `PAUSED`.

Состояние героя моделируется отдельно: `AUTONOMOUS`, `ARENA`, `SAIL`, `DUNGEON`, `BOSS_FIGHT`, `PENSION_TRADER` и `UNKNOWN`. Неизвестный или конфликтующий режим блокирует рекомендации о запуске другого режима.

Рекомендуемый порядок правил: сохранность резерва; критическое здоровье; сопровождение уже начатого режима; допустимое применение предмета; предложение арены, плавания или подземелья; пенсионные операции; отсутствие действия. Этот порядок является исходной политикой продукта, а не фактом игровой механики.

Для арены, плавания, подземелья, босса, инвентаря и пенсионных операций существует отдельный контракт предпосылок. Рекомендация выдаётся только при наличии всех требуемых полей и известной верхней границы стоимости. Для неизвестного предмета, цены, режима, карты или таймера результат всегда `NoOp`.

## 7. Модель праны и зарядов

Прана и заряды — разные величины:

- **прана** — текущий игровой ресурс героя с собственной фактической ёмкостью;
- **заряд** — отдельная единица, которая при ручном использовании может восполнить некоторый объём праны по действующим правилам игры.

Нельзя считать процент праны числом зарядов или списывать стоимость режима непосредственно из баланса зарядов. Для рекомендации сначала определяется дефицит праны до требуемого уровня, затем по подтверждённому контракту конвертации вычисляется худшее число зарядов с учётом фактической ёмкости праны и округления. Если ёмкость, правило конвертации или текущий баланс неизвестны, платная рекомендация запрещена.

Исходный баланс 334 заряда сообщён владельцем и считается доверенным ручным вводом до фактической сверки; жёсткий остаток — не менее 100. При таком подтверждённом балансе арифметическая верхняя граница расхода составляет 234 заряда, но это не целевой бюджет и не обещание срока работы. Бухгалтерское условие:

`доступно = max(0, подтверждённый баланс - 100 - открытые резервы - буфер неопределённости)`.

Резерв создаётся на худшую стоимость рекомендации до её отправки. После ручного действия владелец подтверждает фактическую дельту: резерв заменяется подтверждённым расходом либо освобождается. При неоднозначном результате резерв остаётся заблокированным. Регенерация, награды, возвраты и будущие бесплатные заряды не учитываются заранее. Исключений «на экстренный случай», позволяющих опуститься ниже 100, нет.

Начальные продуктовые лимиты предлагаются как конфигурация, а не как факты игры: `max_charges_per_day=2`, `max_charges_per_rolling_7d=10`, `max_charges_per_expedition=1`. Вход в режим пропускается, если лимита недостаточно для безопасно ограниченного дискреционного бюджета. Частота уведомлений регулируется отдельно. Жёсткий остаток 100 изменяется только явным изменением конфигурации владельцем, с аудитом.

Один глобальный writer сериализует все бюджетные события SQLite-транзакциями. Внешний ручной расход владелец может совершить вне системы, поэтому абсолютная гарантия остатка невозможна. Расхождение ожидаемого и введённого фактического баланса немедленно блокирует новые платные рекомендации до сверки.

## 8. Браузерный исполнитель

Этот раздел фиксирует технический контракт opt-in контура, использование которого конфликтует с правилами игры.

После выполнения допущения о разрешении исполнитель может быть отдельным образом Node.js/TypeScript с Playwright. Для одного аккаунта остаются один процесс, один browser context, один actor и SQLite WAL. Состояния действий:

`PLAN -> RESERVE -> PRECHECK -> EXECUTE -> RECONCILE -> CONFIRMED | FAILED_NO_EFFECT | AMBIGUOUS`.

Перед действием требуются свежий разрешённый UI-снимок, совпадение версии наблюдения, видимый доступный элемент, известная худшая цена и достаточный бюджет. Разрешаются только семантические локаторы и белый список действий. Скрытые endpoint, reverse engineering и методы обхода защит не используются.

Аутентифицированный DOM является отдельным условным источником оперативных данных. Он может поставлять отображаемые баланс зарядов, ёмкость праны, карту, таймер и цену только после проверки соответствующего DOM-контракта; наличие этих значений не приписывается официальному API. Неизвестная версия блокирует зависимое действие.

Исполнитель разделяется на `UiObservationAdapter`, `ModeController`, `ActionJournal`, `ChargeLedger` и чистые стратегии. Арена использует детерминированные пороги здоровья и праны; неизвестное условие боя даёт `NoOp`. Подземелье строит граф известных клеток, стен, выходов, опасностей и ограничений хода; неизвестная клетка не считается безопасной. Морская стратегия отдельно моделирует туман, известные клетки, риск и запас ресурса похода. Босс-стратегия включается только при полном capability polygon: распознаны режим, ход, здоровье, допустимые команды и бюджет. Версионированный каталог инвентаря связывает известный предмет, эффект, контекст и политику; неизвестный предмет не активируется. Детали прогрессии задаются профильным документом.

Карта описывается контрактами `MapObservation`, `TurnObservation`, `RouteConstraint` и `RouteProposal`. Маршрутизация проверяется на статических обезличенных фикстурах карт, тумана, конфликтующих указателей и смены хода. Фикстуры не собираются автоматическим сканированием до выполнения условия допустимости UI-контура.

Журнал применяет уникальный `intent_key` для игрового события и типа действия. Если процесс упал после возможного клика, повтор запрещён до сверки наблюдаемого эффекта. Тайм-аут после клика переводит действие в `AMBIGUOUS`; автоматического retry нет. Это даёт at-most-once для выдачи команды самим агентом, но не гарантирует единственность серверного эффекта без idempotency key со стороны Godville.

Один writer и lease с монотонным fencing token исключают одновременные команды собственных компонентов. Они не способны полностью исключить гонку с человеком или другим клиентом. Неожиданная смена режима, баланса или страницы аннулирует план, сохраняет неясный резерв и переводит систему в ручную сверку.

## 9. Контейнер, секреты и эксплуатация

Проектируется один минимальный контейнер MVP и постоянный volume для SQLite и резервных копий. Это описание границ, а не готовый Compose-файл.

API-токен и данные канала уведомлений монтируются как read-only secret-файлы по фиксированным путям. Они не передаются в аргументах, переменных окружения, логах, SQLite или диагностических снимках. Процесс работает без root, с read-only root filesystem и отдельным writable-каталогом данных. База и резервные копии получают права только владельца процесса.

Ежедневно выполняется согласованная резервная копия SQLite через backup API, с ограниченным сроком хранения. Периодически проверяется восстановление в отдельный каталог. Повреждение базы, недоступность secret-файла или невозможность записать журнал переводят систему в fail-closed: наблюдение может продолжаться только без создания рекомендаций, требующих бюджета.

## 10. Телеметрия и пределы обещаний

Структурированные логи содержат идентификаторы наблюдений и правил, но не токен, URL с токеном, полный приватный ответ или личные сообщения. Метрики: возраст последнего наблюдения, состояние API, число рекомендаций по типу, известный баланс, открытые резервы, бюджетная блокировка, расхождение баланса и результат уведомления.

Оповещения требуются при деградации приватного API, `expired`, неизвестной схеме, длительном отсутствии данных, расхождении бюджета, повреждении БД и ошибке резервного копирования.

Система не обещает достижение пенсии, строительство ковчега, победы, доходность, срок расходования 234 доступных зарядов, непрерывную работу API или отсутствие санкций при запрещённой автоматизации. Случайность игры, изменение правил, сброс токена и неполнота API остаются внешними ограничениями.
